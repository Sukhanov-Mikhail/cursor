## Цель

Улучшить работоспособность мобильного приложения автосервиса:  
уведомления по дефектовке и согласованиям, простой сброс паролей, гибкие диагностические листы с визуалом и привязкой к должностям, подгрузка истории авто при сканировании заказ-наряда.

## Доработка 1. Система уведомлений по рекомендациям / дефектовке

### 1.1. Каналы уведомлений

Уведомления должны уходить (с индивидуальной настройкой у каждого сотрудника):

| Канал | Описание |
|---|---|
| В приложении | Push / in-app |
| Яндекс Телемост | уведомление в Телемосте |
| Мессенджер | рабочий мессенджер |
| Почта | e-mail |
| Рабочий стол | desktop / web |

Настройка: **индивидуально по сотруднику** — какие каналы включены.

### 1.2. Роли получателей

- Слесарь / механик  
- Сервисный консультант (СК)  
- Мастер цеха  
- Руководитель механика (при наличии в оргструктуре)

### 1.3. Сценарий A — создана рекомендация / дефектовка

**Триггер:** в заказ-наряде создана рекомендация (дефектовка) по автомобилю.

**Кому уходит уведомление:**
1. Мастеру цеха  
2. Руководителю этого механика  
3. Сервисному консультанту — автору / ответственному по ЗН  

**Содержание уведомления (минимум):**
- номер заказ-наряда  
- автомобиль (марка, модель, госномер / VIN)  
- кратко: какая дефектовка / рекомендация  
- кто создал  
- ссылка / переход в ЗН в приложении  

### 1.4. Сценарий B — СК согласовал диагностику / работы

**Триггер:** сервисный консультант согласовал диагностику (работы и/или запчасти).

**Кому уходит уведомление «обратно»:**
1. Механику, который выполнял диагностику / заявку  
2. Мастеру цеха  

**Содержание уведомления (минимум):**
- номер ЗН и автомобиль  
- список **согласованных работ**  
- список **согласованных запчастей к замене**  
- что **не согласовано** (желательно)  
- кто согласовал и когда  

### 1.5. Критерии приёмки (доработка 1)

- [ ] При создании рекомендации уведомления получают: мастер цеха, руководитель механика, СК  
- [ ] При согласовании СК уведомления получают: механик и мастер цеха  
- [ ] В тексте есть ЗН, авто, суть дефектовки / согласованные работы и запчасти  
- [ ] Каналы (приложение, Телемост, мессенджер, почта, desktop) настраиваются индивидуально  
- [ ] Есть лог: кому, когда, по какому событию ушло уведомление

## Доработка 2. Упрощённый сброс паролей сотрудников

### 2.1. Проблема

Текущая система сброса паролей неудобна для механиков и тормозит работу с приложением.

### 2.2. Требование

Наладить **простую и быструю** систему сброса паролей для сотрудников (в первую очередь механиков).

### 2.3. Ожидаемое поведение (предложение к реализации)

Минимальный целевой сценарий:
1. Сотрудник запрашивает сброс (из приложения / на экране входа)  
2. Либо мастер цеха / администратор сбрасывает пароль в 1–2 клика  
3. Временный пароль или код подтверждения выдаётся быстро (SMS / код руководителю / одноразовый код)  
4. При первом входе — обязательная смена пароля  

### 2.4. Критерии приёмки (доработка 2)

- [ ] Механик может восстановить доступ без длительного обращения в IT  
- [ ] Мастер цеха / админ может сбросить пароль подчинённому  
- [ ] Есть аудит сбросов (кто, кому, когда)  
- [ ] Временный пароль одноразовый / с принудительной сменой  

> Антону: предложить 1–2 варианта UX (self-service vs сброс через мастера) и согласовать с постановщиком до разработки.

## Доработка 3. Диагностические листы + визуальные блоки (иконки)

### 3.1. Требование

Администратор должен иметь возможность:
1. Создавать **новые листы диагностики**  
2. К конкретным пунктам листа прикреплять **визуальные блоки** (иконки / пиктограммы)  
3. Выбирать визуал из **списка действующих**  

### 3.2. Библиотека иконок

Список стандартных значков автосервиса нужно **максимально расширить**, например (минимум):

- двигатель / масло / фильтры  
- тормоза / колодки / диски  
- подвеска / амортизаторы / рычаги  
- шины / давление / износ  
- АКПП / МКПП / сцепление  
- охлаждение / радиатор / антифриз  
- аккумулятор / генератор / стартер  
- кондиционер / салонный фильтр  
- выхлоп / катализатор  
- рулевое управление  
- светотехника / фары  
- кузов / ЛКП / коррозия  
- диагностика ЭБУ / ошибки  
- ремень / цепь ГРМ  
- жидкость ГУР / тормозной жидкости  
- статус: норма / внимание / критично  

### 3.3. Критерии приёмки (доработка 3)

- [ ] Админ создаёт лист диагностики и пункты  
- [ ] К пункту можно привязать иконку из библиотеки  
- [ ] Библиотека содержит расширенный набор стандартных значков автосервиса  
- [ ] В мобильном приложении пункты отображаются с выбранным визуалом

## Доработка 4. Привязка типов диагностических листов к должностям

### 4.1. Требование

Администратор должен уметь привязывать **конкретный тип диагностического листа** к **конкретной должности**.

**Пример:**  
создан лист «Диагностика СК» → должность «Сервисный консультант» →  
у **всех** сотрудников с этой должностью в мобильном приложении появляется возможность создавать этот лист.

### 4.2. Логика

- Один лист → одна или несколько должностей  
- Сотрудник видит в приложении только листы, доступные его должности  
- При смене должности набор доступных листов обновляется  

### 4.3. Критерии приёмки (доработка 4)

- [ ] В админке есть привязка: лист ↔ должность(и)  
- [ ] В мобилке сотрудник видит только разрешённые листы  
- [ ] После назначения должности новому СК лист становится доступен без ручной выдачи поштучно

## Доработка 5. Сканирование заказ-наряда → история авто + рекомендации

### 5.1. Требование

При **сканировании заказ-наряда** в мобильном приложении должна подгружаться:

1. **История автомобиля** из карточки автомобиля  
2. **Актуальные рекомендации** с последнего визита  

### 5.2. Ожидаемый UX

1. Сотрудник сканирует ЗН (QR / штрихкод)  
2. Открывается ЗН  
3. Блоки «История автомобиля» и «Рекомендации с прошлого визита» подгружаются автоматически  
4. Можно сразу использовать рекомендации в текущем визите (просмотр / продолжение / закрытие — уточнить с постановщиком)

### 5.3. Критерии приёмки (доработка 5)

- [ ] После сканирования ЗН история авто доступна без ручного поиска карточки  
- [ ] Подтягиваются актуальные рекомендации последнего визита  
- [ ] Если истории/рекомендаций нет — корректное пустое состояние (не ошибка)
